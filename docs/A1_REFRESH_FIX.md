# A1 四色屏中间竖带修复

2026-10-24，在一块用户确认的 A1 四色屏上，替换完整显示流程后，中间竖向明暗带消失。恢复 ESP32-C3 板载 3.3 V 供电，再对同一张照片强制刷新，用户确认“仍然正常，没有中线”。这次对照支持旧固件 A1 驱动流程不匹配是关键原因，外接稳压不是这台设备消除中线的必要条件。尚未把问题归因到单个寄存器，也没有对所有屏幕批次作相同保证。

## 修复内容

| 路径 | 原流程 | 本次适配 |
|---|---|---|
| 初始化 | A1 仍执行简短的通用初始化 | 完整 A1 解锁、驱动参数和扫描窗口序列 |
| 图像写入 | 逐行选择隔行窗口，单字节切换 CS | 768×552 写入窗口，一次 `0x10`，连续 CS 下传完 105,984 字节 |
| 刷新区间 | 原扫描流程 | TRES 与最终窗口保持参考流程的 768×600；实际照片仍为 768×552 |
| 刷新完成 | 等待当前 BUSY 释放 | 至少 14 秒保护，观察到 BUSY 拉低并连续 500 ms 空闲后才能继续 |
| 关屏完成 | 短等待后可能提前休眠 | 观察 `0x02` 后 BUSY 拉低及稳定释放，再发 `0x07,0xA5`；超时不记录成功 |
| 文件错误 | 行读取长度未逐次确认 | 精确长度检查、每行严格读取、前后两次 CRC16 一致后才刷新 |

适配沿用现有软件 SPI 单字节 HAL，不声称已经迁移为 Moink 的 4 MHz 硬件 SPI。输入帧沿用现有服务端线序，不再额外旋转或镜像。RST 仍为 GPIO2，SCK4、MOSI6、CS7、DC1、BUSY10；不能套用其他方案的 RST3 接法。

CRC16 在这里用于本地文件的读取一致性，不是新加的网络帧协议。服务端仍通过现有 InkSight 2bpp 接口发送照片，不要求 Moink 的 16 字节帧头。A0 入口保留并经过指令级检查，本次没有 A0 实屏验收。

## 立即刷新

现有设备用 `X-Preview-Push: 1` 表示强制刷新。服务端成功消费手动刷新请求时，同时返回 `X-Pending-Refresh: 1` 和这个兼容头，使内容相同也能重新刷屏；普通轮询沿用 SHA 去重。渲染失败或鉴权失败不消费请求，也不发强制刷新头。无需修改设备配置、照片记录或数据库结构。

## 实机对照

| 条件 | 观察 |
|---|---|
| 原驱动，增加独立 3.3 V 稳压 | 中线仍然存在，用户反馈 |
| 完整 A1 流程，保留独立稳压 | 同张照片恢复正常；刷新等待 15,280 ms，关屏等待 170 ms，总显示流程 18,696 ms |
| 完整 A1 流程，恢复 C3 3V3/GND 原接线 | 再次强制刷新同张照片；刷新等待 15,290 ms，关屏等待 170 ms，总显示流程 18,704 ms；用户确认没有中线 |

刷入时仅更新 app0，回读逐字节一致；NVS、文件系统、分区表和 OTA 元数据在启动前前后相同。设备重新联网，8.5 dBm 设置保留。这里记录状态和时序，不公开设备标识、照片、网络配置或备份内容。

## 构建、验证与回退

源码和具体命令见 [固件适配目录](../firmware/esp32-c3-a1/README.md)。这是针对固定基线的兼容补丁：

- 输入应用 SHA-256：`52a4c30da2dc0aec87da317d5a0cd22895535c1dfdbad43c48a8f32584a01af0`。
- 已验收输出应用 SHA-256：`befb5bd8e02547f2ab21f36272e75e9b613e1a6f1c60130c6756bf1529023c10`。
- 源码构建需自行持有匹配基线；已验收应用升级包见 [GitHub Release](https://github.com/3dhaoxinren/miaomo-server/releases/tag/firmware-c3-a1-20261024)，附刷写、接线与固件参考说明。构建工具对错误基线拒绝输出，不自动刷机；设备 flash 备份不公开。
- 离线验证执行生成的 RV32 指令，检查初始化字节、CS 包络、完整载荷、延迟 BUSY、超时、短读和内容变化等 16 个场景；模拟外设不等于电气实测。
- 更新前保存应用分区备份；实屏若异常，恢复相同 app0 地址的原应用并回读校验。不要擦除全片或覆盖 NVS、分区表、文件系统。地址和分区大小必须与工具说明的固定基线匹配。

本次只替换显示流程，保留 InkSight 局域网连接方式。Moink 的网页更新、OTA、HTTP 上传和并发实现并未作为这次修复代码引入；它们的保护声明需要分别审查。
